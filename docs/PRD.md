## 1. 背景与目标

### 1.1 背景

公司需要一个对外的官方网站，用于承接各类 Web 开发业务的市场推广：让潜在客户在站内即可了解「我们能做什么」「做过什么」「怎么联系我们」，从而产生询盘。

### 1.2 产品目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 清晰展示可承接的开发服务范围 | 服务页覆盖 ≥ 6 条服务线，每条含能力说明与交付物 |
| G2 | 用成功案例建立信任 | 案例列表 + 独立详情页，每案含背景/方案/技术栈/量化结果 |
| G3 | 转化：访客能低成本发起咨询 | 每页可见联系入口，联系页含表单（mailto 兜底）与多渠道联系方式 |
| G4 | 面向海外客户 | 简体中文 / English / 日本語 三语，默认中文 |
| G5 | 零运维成本、稳定可用 | 纯静态托管于 GitHub Pages，`release` 分支一键部署 |
| G6 | 内容可维护 | 所有文案/案例/服务集中在配置文件，改内容不改组件代码 |

### 1.3 目标用户

| 用户 | 诉求 | 对应内容 |
| --- | --- | --- |
| 中小企业/创业公司负责人 | 找靠谱团队做官网/后台/小程序 | 服务页、案例、流程、联系 |
| 企业技术/产品负责人 | 评估技术能力与协作方式 | 案例详情（技术栈、架构、结果）、关于页 |
| 海外客户 | 英文/日文可读 | 三语完整覆盖 |

## 3. 页面信息架构与路由

站点为**多页结构**，URL 首段为 locale；静态导出启用 `trailingSlash`。

| 路由 | 页面 | 说明 |
| --- | --- | --- |
| `/` | 语言跳转 | 客户端按 Cookie → `navigator.language` → `zh-CN` 跳转 |
| `/{locale}/` | 首页 | Hero、服务概览、精选案例、合作流程、客户评价、CTA |
| `/{locale}/services/` | 服务 | 服务线列表 + 每条服务的锚点详情（能力/交付物/适用场景/技术栈） |
| `/{locale}/cases/` | 成功案例 | 案例卡片列表，可按行业/服务类型筛选（客户端） |
| `/{locale}/cases/{slug}/` | 案例详情 | 背景、方案、实施、技术栈、成果数据、相关案例 |
| `/{locale}/about/` | 关于我们 | 公司简介、数据指标、发展里程碑、团队/价值观、资质 |
| `/{locale}/contact/` | 联系我们 | 联系表单（生成 mailto）、联系方式、社交渠道、FAQ |
| `/{locale}/privacy/` | 隐私政策 | 法务模板页 |
| `/{locale}/terms/` | 服务条款 | 法务模板页 |
| `*` | 404 | 返回首页 / 服务 / 案例的引导 |
| `/admin/` | 主题设置（内部工具，不计入三语路由） | 明暗模式 + 12 色预设 + 取色器，偏好存 `localStorage` |

`locale ∈ {zh-CN, en, ja}`。导航项指向**页面路由**（多页站点），首页内部区块使用锚点。

### 3.1 首页区块顺序（可配置）

`hero → services → featuredCases → process → testimonials → cta`

## 4. 功能需求

### FR-01 多语言（P0）

- 三语：`zh-CN`（默认）、`en`、`ja`；切换语言保留当前路径语义（案例详情切换后仍停在同一篇案例）。
- 语言协商优先级：Cookie `NEXT_LOCALE` → `Accept-Language` → 默认中文；根路径 `/` 做客户端跳转。
- **内容对齐**：三语的案例 slug、服务 id、导航结构必须一一对应，构建前用脚本校验（parity check），缺项即构建失败。

### FR-02 首页（P0）

- Hero：徽标胶囊、主标题、副标题、主/次 CTA、渐变或网格背景（可配置）。
- 服务概览：卡片网格，图标 + 标题 + 摘要，点击进入服务页对应锚点。
- 精选案例：3–6 个案例卡（封面、行业、标题、结果指标），进入案例详情。
- 合作流程：4 步（沟通 → 方案 → 开发 → 交付运维）。
- 客户评价：3 条占位评价卡（头像/星级/引用）。
- 结尾 CTA：引导至联系页。

### FR-03 服务页（P0）

- ≥ 6 条服务线（占位）：企业官网与营销站、Web 应用开发、后台管理系统、电商与小程序、移动端 H5/跨端、长期运维与技术支持。
- 每条含：图标、一句话摘要、能力点列表、交付物列表、适用场景、常用技术栈标签。
- 支持锚点直达 `#service-{id}`。

### FR-04 案例列表与详情（P0）

- 列表：≥ 6 个占位案例，卡片含封面图、标题、行业、服务标签、一条量化结果。
- 客户端筛选：按行业 / 服务类型（无后端，纯前端过滤）。
- 详情：项目背景、解决方案、实施过程、技术栈、成果（2–4 个量化指标）、相关案例推荐。
- 未命中 slug 时返回 404（静态生成阶段即兜底）。

### FR-05 关于页（P1）

- 公司简介（多段）、3–4 个数据指标、发展里程碑时间线、价值观卡片、团队占位。

### FR-06 联系页（P0）

- 表单：姓名、邮箱、公司、预算（可选）、需求描述；提交通过 `mailto:` 生成预填邮件（纯静态，无后端）。
- 联系方式区：邮箱、电话、地址、社交链接，图标磁贴样式。
- 常见问题 FAQ（`<details>` 折叠，4–6 条）。

### FR-07 全站导航与页脚（P0）

- 粘性导航：滚动后磨砂背景（`backdrop-blur`），Logo、主导航、语言切换、CTA 按钮、移动端汉堡菜单（含 ESC 关闭与焦点管理）。
- 页脚：品牌简介、多列链接（服务/案例/公司/法务）、社交、版权、返回顶部。

### FR-08 404（P0）

- 三语文案 + 返回首页 CTA + 常用链接。

### FR-09 SEO 与分享（P0）

- 每页独立 `title` / `description` / `keywords` / canonical / `hreflang`（含 `x-default`）。
- Open Graph + Twitter Card，`ogImage` 占位图。
- `sitemap.xml`、`robots.txt`、favicon（SVG + ICO）。
- 结构化数据：Organization（全站）、Service/Breadcrumb（服务页）、Article + Product/Review 语义（案例详情）。

### FR-10 主题与视觉（P0）

- 视觉语言：亮色基底（默认，可在 /admin 切换暗色）、`page`/`band` 交替分区、单一品牌蓝主色、卡片 `1rem` 圆角 + 1px 描边 hover 上浮、磨砂导航、克制的径向渐变 Hero、lucide 图标。
- 主色可通过配置切换（12 色预设 + 取色器，入口 `/admin/`），浅/深两种模式，偏好存 `localStorage`，无闪烁应用。

### FR-11 无障碍（P0）

- 每个 `<section>` 带 `aria-labelledby`；所有可交互元素 `focus-visible` 焦点环；移动菜单 `aria-expanded/controls`；语义化标题层级；对比度达 WCAG 2.1 AA；尊重 `prefers-reduced-motion`。

### FR-12 性能（P0）

- 纯静态、无第三方追踪脚本；图片懒加载并提供宽高避免 CLS；Lighthouse 移动端 Performance ≥ 90、Accessibility ≥ 95。

## 5. 内容与占位策略（P0）

- 所有可见文案集中在 `config/locales/{zh-CN,en,ja}.json`（站点配置层）与 `messages/{locale}.json`（UI 短字符串层）。
- 案例、服务为结构化数据，由 Zod schema 校验；缺失字段、非法图标名、三语 slug 不一致均在 `npm run validate` / `npm run check:i18n` 阶段报错。
- 占位图片使用本地 SVG/渐变占位，避免版权问题；替换真实素材时只改配置里的路径。

## 6. 非功能需求（NFR）

| 类别 | 要求 |
| --- | --- |
| 性能 | 首屏 LCP < 2.5s（4G 模拟），JS 体积受控，无运行时框架外依赖 |
| 可用性 | 静态资源由 GitHub CDN 分发，可用性依赖 Pages SLA；构建失败不影响线上旧版本 |
| 兼容 | 最近两个版本的 Chrome / Safari / Firefox / Edge；iOS Safari & Android Chrome 主流版本 |
| 无障碍 | WCAG 2.1 AA |
| 安全 | 无后端、无密钥入库；表单仅 mailto，不收集敏感信息；依赖无高危漏洞 |
| SEO | 三语页面可被索引，`hreflang` 正确，无重复内容 |
| 可维护 | 新增一个案例/一条服务 = 只改配置文件 |

## 7. 发布需求

- **只有 `release` 分支的 push 触发自动部署**到 GitHub Pages；`main`/`dev` 不触发。
- 支持手动 `workflow_dispatch` 触发，便于重发与排障。
- 构建前执行质量门禁（validate / i18n 校验 / lint / typecheck / test），任一失败即中止，线上不受影响。
- 仓库 Settings → Pages 的 Source 必须设为 **GitHub Actions**（一次性人工配置，见 DEVELOPMENT.md §5）。

---

## 8. 验收标准（Release Gate）

1. 三语切换后当前页面语义保持一致，无缺失文案（parity 脚本通过）。
2. 全部路由在 `npm run build`（静态导出）后存在于 `out/`，404 页可用。
3. 质量门禁全绿：`validate`、`check:i18n`、`lint`、`typecheck`、`test`。
4. `release` 分支 push 后 Actions 自动构建并部署，站点可访问；`main`/`dev` push 不触发。
5. 移动端（375px）与桌面端（1440px）无横向溢出，导航/菜单可用。
6. Lighthouse：Performance ≥ 90、Accessibility ≥ 95（移动模拟）。
7. 所有占位内容可在一个配置文件内被替换，无需改组件代码。

---

## 9. 明确不做（Out of Scope，一期）

- 后端服务 / 数据库 / API 路由 / Server Actions（静态导出不可用）。
- 表单真实提交（一期用 `mailto:`，二期可接第三方表单服务）。
- CMS、博客/文章系统、在线支付、用户登录。
- 服务详情独立子页（一期用服务页内锚点，二期按 SEO 需要拆分）。
- 真实商业素材与客户授权（当前为占位内容）。
